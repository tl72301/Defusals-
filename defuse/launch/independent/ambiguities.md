# Ambiguities in LAUNCH_PROTOCOL.md sections 3-4 and how indep_engine.py resolves them

1. Freshness boundary: is a reading usable when t equals the observation time + 15 exactly? I treat it as fresh (t <= oldest + 15, or + 60 for solar), as the brief says.
2. Because freshness uses the older end, a '15-29' reading (older end r-29) can never be fresh for the 15-minute items (it can still start a field mill wait, and solar stays fresh until r+31). The text does not say whether this is intended. I apply it literally.
3. In "violated if all definite readings show a violation", I require at least one definite reading, and an 'unclear' latest reading from another source does not stop a violation. An 'unclear' reading only stops "met".
4. "Each source's latest": latest by report time, with ties broken by comparing the id strings, which is not natural order ('r10' sorts before 'r9'). Latest by observation time would be the other reading. A same-source 'unclear' latest reading hides that source's older fresh definite reading.
5. LIGHTNING and FIELDMILL "met if a fresh definite reading exists": I check only each source's latest fresh reading. An 'unclear' latest reading from another source does not stop "met". The text could also mean any fresh reading at all, or that 'unclear' should block, as it does for WIND.
6. 'beyond10' gives no lightning reading. It is not definite, it is not 'unclear', and it does not count as restating the item for a correction.
7. Lightning bins count from the report time, so OBS_TIME does not move the strike time. The latest possible strike time is r, r-10 or r-20. The protocol's "waiting periods use the newer end" could be read as also shifting by the OBS_TIME age. I do not shift.
8. Lightning waits come from any statement not removed by a correction, whether or not it is fresh. But "30+ readings are expired" conflicts with "regardless of freshness". I excluded '30+' reports from starting lightning and field mill waits.
9. Field mill wait: violated while t < newest observation time + 15. This is strict, so the wait ends exactly at +15. The lightning wait is strict at +30 in the same way.
10. HEAT "last 30 minutes": I use the 30 integer minutes t-29..t, including t. The other readings would be 31 minutes (t-30..t) or a window that excludes t.
11. HEAT "both levels have a current status": I take this to mean each level's limit status at t is met or violated, not insufficient. So HEAT is insufficient whenever either level lacks a fresh, unanimous, clear reading at t, even if a cool minute earlier in the window would otherwise give met.
12. HEAT per-minute history: minute m uses only reports with minute <= m, evaluated at m, so a correction is not applied to earlier minutes. Clarifications that arrived by t are applied to every earlier minute. Minutes before 0, or with no fresh data, are unknown. They block "violated" but not "met".
13. Corrections: "earlier" means earlier by (minute, id). A correction removes the same source's readings of each item it mentions, including 'unclear' mentions. It also does this when its own OBS_TIME is '30+'. CORRECTION 'unclear' is treated as not a correction.
14. TEMP_LOW and TEMP_HIGH count as separate items for corrections. A correction that restates only one level does not remove the other level's earlier reading.
15. Clarifications replace that report's answer to that question from arrival onward. This covers OBS_TIME too, which changes freshness and waits for all of the report's items. If several overrides target the same report and question, the latest arrival wins, with ties broken by list order. An override to 'not_mentioned' removes the reading.
16. A report that has no answers dict gets every item 'not_mentioned', OBS_TIME 'current' and CORRECTION 'no'.
