# Allergy Pass: protocol and pre-registration

A research simulation. During a modeled dinner service, messages about one order arrive from the server, the guest,
the delivery app, the host, the manager and the kitchen. A language model answers multiple-choice questions about each
message; code applies US allergen definitions, the restaurant's recipes and what is in the fryer oil, and decides for
every dish on the order whether it may be sent. **This is not food-safety advice, and "send" here never means a dish
is safe for a real person.**

It repeats the design of Launch Window (LAUNCH_PROTOCOL.md) with a familiar subject. This file was committed before
any message text existed. Changes after that point are listed at the end with their reasons.

## 1. Rules and sources

All checked against primary sources on October 12, 2026.

| Rule | Source |
|---|---|
| Nine major food allergens: milk, egg, fish, crustacean shellfish, tree nuts, wheat, peanuts, soybeans, sesame | 21 U.S.C. 321(qq)(1) (FALCPA 2004; sesame added by the FASTER Act 2021, from January 1, 2023) |
| What each covers: milk from cows, goats, sheep or other ruminants; eggs of chickens, ducks, geese, quail or other fowl; wheat is any *Triticum* species (spelt, durum, einkorn, emmer, khorasan, triticale); molluscs are not major allergens | FDA, *Questions and Answers Regarding Food Allergens*, Edition 5, final guidance, January 2025 (C.1, C.3, C.9, B.9) |
| Tree nuts: only the 12 in FDA's Table 1 (almond, black walnut, Brazil nut, California walnut, cashew, filbert/hazelnut, heartnut, macadamia, pecan, pine nut, pistachio, walnut); coconut and chestnut are no longer on the list; peanuts are legumes | Same guidance, C.8; FDA FAQ, March 26, 2025 |
| Cross-contact: an allergen unintentionally incorporated into a food; shrimp protein transfers to fries cooked in the same oil | 21 CFR 117.3; FDA seafood hazards guidance, chapter 19 (2019); FARE guidance on shared fryers |
| Restaurants tell consumers about major allergens in unpackaged food | FDA Food Code 2022 and 2026, 3-602.12(C) |

**Modeling choices (each narrows or simplifies; none is a claim about real practice):**

- Only the nine major allergens are tracked. Molluscs, refined-oil exemptions and allergies outside the nine are not
  modeled, and no message plan uses them, so no scenario turns on them.
- "Shellfish" means crustacean shellfish. "Gluten-free" and celiac disease mean avoiding wheat. Lactose intolerance
  is treated as avoiding milk (a restaurant policy choice; it is not a legal requirement).
- A restriction applies to everyone's food on the order (the order is shared).
- The fries oil starts each service shared with breaded chicken tenders (wheat). The kitchen may announce fresh oil
  or a dedicated fryer (empties the oil), or something else fried in it (added to the oil).

## 2. The simulation

Each scenario is one order during 60 simulated minutes: a dine-in table or a delivery order, with three or four dishes
from a fixed menu of 19 dishes whose allergens and fries are known to code only. Hidden truth: which allergens the
people eating the order must avoid (some only from the minute a late diner joins), and what is in the fries oil when.

About 17 messages arrive per scenario: the order note; follow-ups from the guest; a server relay; kitchen chat (fryer
announcements, read-backs, other tables' allergies, routine chatter); a host or manager note; other tickets' notes; and
two (original style) or three (harder style) planted traps, drawn from documented restaurant failures:

| Trap | What the message does | What the answer key says |
|---|---|---|
| Vague | "nut allergy" or "seafood allergy" without saying which | both categories `unclear` |
| Correction | an earlier message wrongly adds a restriction; a later one explicitly corrects it ("scratch that") | `avoid`, then `ok` with CORRECTION `yes` |
| False assurance | a server or manager says a real restriction is fine, without any correction wording | `ok`, CORRECTION `no` (the code keeps the restriction) |
| Scope | the guest mentions someone who is not eating this order | `not_mentioned` |
| Other table in the same message | "Table 12 no dairy; Table 9 no eggs" | only this order's allergen |
| Fryer unclear | "something else just went into the fries oil, not sure what" | FRYER `unclear` |
| Misspoken (harder style only) | "allergic to sesame, sorry, I mean soy" | only the corrected item |

The **harder style** also words allergens by derived or specific names (ghee, whey, tahini, aioli, semolina, celiac,
pistachios, anchovies, prawns) and adds traps. Plans are generated by code (`defuse/allergy/sim.py`) from fixed seeds.

## 3. What the model is asked

Eleven multiple-choice questions per message. The instructions name the order, explain the four allergen answers
once and give the FDA definitions:

- For each of the nine allergens: `not_mentioned`, `avoid` (someone eating this order must avoid it: an allergy, an
  intolerance or a request for none), `ok` (the message says it is fine for everyone eating this order), `unclear`
  (it may be meant, but the message does not make clear whether it must be avoided, e.g. "nuts" without saying which).
- FRYER: what does the message say about the fries oil? `not_mentioned`, `fresh`, `wheat`, `shellfish`, `fish`,
  `unclear`.
- CORRECTION: does the message explicitly correct, replace or withdraw something said earlier about this order's
  allergies? `no`, `yes`, `unclear`.

The model never sees recipes, never combines messages and never decides whether a dish is safe.

## 4. The protocol (code, identical for every system)

1. **Restrictions.** Messages are applied in time order. `avoid` always applies. `unclear` applies unless the
   allergen is already to be avoided. `ok` clears an `unclear`, but lifts an `avoid` only in a message with
   CORRECTION `yes`: an unexplained reversal is not trusted.
2. **Fryer.** Starts as wheat. `fresh` empties the oil and clears doubt; `wheat`, `shellfish` or `fish` adds to it;
   `unclear` makes the contents unknown until the next `fresh`.
3. **Pass checks.** Every 5 minutes from minute 20 to minute 60 (9 checks), each dish on the order is decided: **hold**
   if it contains an allergen to avoid (as an ingredient, or through the fries oil); else **ask** if it contains an
   unclear allergen, or comes with fries while the oil is unknown and the order has any restriction; else **send**.
4. **Clarifications.** When a system answers `unclear` for an allergen or the fryer, it may ask the sender; a
   templated reply arrives 2 minutes later and is read by the same system. At most 4 per order.

**Scoring.** At each check, each system's decision is compared with the *justified* decision: what the answer key's
evidence (including the replies that system received) supports. A **false clear** is a dish the system would send when
the justified decision is hold or ask. Decisions against the hidden truth are reported as a diagnostic only.

## 5. Messages and answer keys

Separate author agents write each message's text from its plan ("must convey" lines), without seeing answers, code
or results. Separate blind reviewers answer all 11 questions from the text alone. Where a reviewer disagrees with the
key, a second, fresh reviewer answers that message; the message is kept only if the second reviewer agrees with the
key, otherwise it is dropped (listed in `defuse/allergy/bank/excluded.json`). Scenarios are not dropped.

## 6. Systems compared (same messages, protocol code, clarification budget and delay)

| System | Extraction |
|---|---|
| decisions | OpenAI Decisions API (`gpt-6-luna`), all 11 questions in one request |
| responses-options | the same model through the ordinary Responses API, reasoning off, choosing from the same options (strict JSON schema with the same descriptions) |
| responses-names | the same model through the ordinary Responses API, reasoning off, writing each food name as worded plus avoid / ok / unclear, the fryer item as worded, and the correction flag; code maps names to categories with a lexicon frozen before any text existed (`defuse/allergy/lexicon.py`) |
| parser | keyword parser written and committed before any message text existed (`defuse/allergy/parser.py`) |
| oracle | the answer key (diagnostic ceiling, not a competitor) |

## 7. Pre-registered analysis

- **Splits.** Development: 2 original-style (seeds 1001–1002) and 2 harder (1101–1102) scenarios, used only for
  smoke tests. Test: 60 original-style (2001–2060) and 60 harder (2101–2160) scenarios, 2,090 messages.
- **Primary measures.** (1) Accuracy per answer on the 10 factual questions (9 allergens and the fryer), with Wilson
  95% intervals. (2) False clears and wrong decisions over all dish checks. (3) Cost per 1,000 messages from reported
  token usage at list prices, clarifications included.
- **Secondary.** Accuracy on all 11 questions; per question; per trap; share of messages with every factual answer
  right; median latency; for Decisions, accuracy by top-answer probability.
- **Comparisons.** Each pair of the three model systems on the same factual answers: exact two-sided McNemar test,
  Holm-corrected over the three pairs, α = 0.05. No directional prediction. The question carried over from Launch
  Window is whether letting code hold the knowledge (here: which foods belong to which FDA category) again beats
  asking the model to choose the category.
- **Runs.** One run per system on the test set, after development smoke tests. No tuning.
- **Budget.** The project's $4 cap leaves about $1.58; request sizes project about $1.20 for the test set. If the
  development smoke tests project more than $1.30, test scenarios are removed from the end of both test splits in
  equal numbers before any test request. The budget gate refuses any request that would pass the cap.
- **Publishing either way.** Results are reported whatever the outcome.

## 8. Changes after pre-registration

1. **Three ambiguous messages dropped before review and before any test request.** One author noticed that in three
   scenarios the "not eating with us" relative had the same relation word ("my aunt") as a diner who had joined and
   was eating, so a reader could take them as the same person. The generator chose both relations independently. The
   three messages (A2013-04, A2133-10, A2151-12) are dropped; their scenarios stay. Test set: 2,087 messages.
2. **Development messages are not blind-reviewed.** They are used only for the smoke tests (§7), never in results.
   The smoke tests (66 messages, all systems) cost $0.036, projecting about $1.12 for the test set, under the $1.30
   limit, so no test scenario is removed.
3. **One post-hoc check, after the results (not pre-registered).** No system sent an unsafe dish, so I measured how much
   of that came from the code's rule that an unexplained "it's fine" never lifts a restriction: the same readings were
   replayed with a rule that trusts every "it's fine" (`defuse/allergy/counterfactual.py`). Reported as exploratory.
4. **Exploratory reanalysis, October 19 (not pre-registered).** Four independent reviews of the design, and a free
   replay of the archived readings: accuracy on answers where something was said, outcomes per order, errors per
   trap, Decisions-first hybrid policies, single-mention replays and how much the rule leans on the correction
   question (`defuse/allergy/exploratory.py`). It reuses the test set, so it is reported as exploratory and motivates
   §9 rather than confirming anything.

## 9. Who can cancel an allergy? Pre-registration of October 19, 2026

Committed before any message text for this test existed, after the reanalysis in §8 change 4 and a search for similar
published work. Everything not stated here is as in §1 to §7: the same menu, definitions, 11 questions, prompts,
systems, clarification rule and delay, and pass checks. Code: `defuse/allergy/cancel.py` (plans),
`rules.restrictions(..., rule)` (the rules), `defuse/allergy/cancel_report.py` (this analysis).

**Prior work.** A search on October 19 (44 queries across GitHub, arXiv, blogs and portfolios; report in
[docs/prior-work-2026-10-19.md](docs/prior-work-2026-10-19.md)) found no study of who may cancel a stated allergy, and
none comparing cancel rules on fixed model readings. Nearest: OrderBench (single restaurant-order messages, code-free
scoring of unsafe acceptances), Risky-Bench (an injected "ignore the allergy flag" attack on a delivery agent), a study
of an allergy mentioned once surviving memory compression, and untested 0.9-probability fallbacks offered for the
Decisions API.

### 9.1 Question

When an allergy has been stated once and someone later says that food is fine, which rule keeps people safe at the
lowest cost, and does the reading model change the answer? The October 12 test could not say: every allergy was
repeated, every false reassurance was worded plainly, and the code let any message worded as a correction cancel an
allergy, whoever sent it.

### 9.2 Three rules, applied by code to the same readings

| Rule | When an "it's fine" (`ok`) counts |
|---|---|
| `anyone` (the October 12 rule) | from any sender; it lifts an `avoid` only with CORRECTION `yes` |
| `guest_only` | only from the guest's own side (their texts and their delivery-app notes); same correction condition |
| `same_sender` (secondary) | from the guest's side, or from the sender who first stated that allergy |

Under `guest_only` and `same_sender` a staff `ok` also no longer clears an `unclear`. The sender is the message header's
source, which code knows; the model is not asked about it.

### 9.3 Orders

300 test orders (seeds 3101–3400) and 5 development orders (3001–3005, one per arm, smoke tests only). One allergen per
order, stated in exactly one message: the order note (about half), a guest text, or a host or manager note. Each order
has 3 or 4 dishes, one or two of which contain that allergen. Distractors: two other orders' allergies, a relative who
is not eating (half the orders), kitchen chatter, a routine note about this order, and fryer news (40%). Arms, assigned
by a fixed shuffle:

| Arm | Orders | What happens between minute 12 and 35 | Truth | Answer key for that message |
|---|---:|---|---|---|
| control | 60 | nothing more about the allergen | allergy | – |
| guest_takes_back | 40 | the guest explicitly takes back their own mistaken allergy | no allergy | `ok`, CORRECTION `yes` |
| staff_fixes_own | 40 | the staff member who wrote the allergy explicitly corrects it | no allergy | `ok`, CORRECTION `yes` |
| staff_wrong_correction | 40 | a staff member explicitly "corrects" it, wrongly (half the time the same sender) | allergy | `ok`, CORRECTION `yes` |
| staff_soft | 120 | a staff member casually says it is fine ("actually…", "turns out…"), banned from correction words | allergy | `ok`, CORRECTION `no` |

staff_fixes_own and staff_wrong_correction use identical "must convey" lines, so the text cannot tell them apart. With
the answer key's readings the rules give, by construction: `anyone` sends the allergen in all 40 wrong corrections;
`guest_only` sends none and holds the dish needlessly in all 40 staff self-fixes; `same_sender` sends it in the wrong
corrections that came from the original sender. What the test measures is whether real readings change that picture:
a missed single mention (unsafe under every rule), a casual reassurance read as a correction (unsafe under `anyone`), or
a genuine take-back misread (a needless hold under every rule).

### 9.4 Messages

As in §5: separate blind author agents write each message from its plan; separate blind reviewers answer the 11
questions from the text alone; a disagreement goes to a fresh second reviewer and the message is dropped unless that
reviewer agrees with the key. If review drops more than 15% of an arm's cancel messages, that arm is reported with the
drop rate as a finding (its wording is ambiguous to careful readers too). Dropped single mentions or cancel messages
drop their whole order, because the order then tests nothing.

### 9.5 Systems and runs

The three model systems of §6, unchanged, plus the parser and the answer key. One more policy, scored from the saved
answers at no extra cost: **hybrid** = Decisions first; any answer whose top probability is below **0.9** (the Launch
Window cut, fixed here before any data) is replaced by the ordinary API's (picking options) answer to the same
question. The hybrid's cost counts the second reading for every message that needed one; its time adds that reading's
time.

Two runs: the full test set once, then a repeat of all three model systems with a separate cache (`--tag -r2`) to
measure run-to-run change. The first run is the result; the repeat is reported beside it.

### 9.6 Analysis (pre-registered)

Outcomes per order, against the hidden truth, at the pass checks from the cancel message's minute on (every check in
control orders): **unsafe** = any dish sent that the truth says hold or ask; **needless stop** = any dish held or sent
back to ask that the truth says send.

- **Primary.** For each model system, `anyone` against `guest_only` on its own readings, paired by order: orders unsafe
  and orders with a needless stop, exact two-sided McNemar, Holm over the 6 tests, α = 0.05. Expected direction:
  `guest_only` fewer unsafe orders and more needless stops.
- **Secondary.** (a) Single mentions read as neither `avoid` nor `unclear` (missed), by system and by where it was
  stated; pairwise exact McNemar, Holm over 3. (b) staff_soft cancel messages read as CORRECTION `yes`, by system;
  same test. (c) Hybrid against Decisions and against picking options on the answers whose key is not
  `not_mentioned`, paired; Holm over 2; plus cost per 1,000 messages and median and 90th-percentile time. (d) Each
  arm's outcomes under all three rules, and the parser and answer key as references. (e) Factual accuracy, accuracy
  where something was said, messages with every answer right. (f) Answers that changed between the two runs.
- Every rate with its denominator and a Wilson 95% interval.

### 9.7 Budget

A fresh approval of **$4.00** for this work, separate from the about $3.55 spent before, set in `defuse/budget.py`;
every paid request goes through it. Request sizes project about $1.20 per full run of the three systems on about 2,145
messages, clarifications included, plus about $0.02 for the smoke tests. If the smoke tests project more than $1.80 per
run, the repeat run is dropped; if they project more than $3.50 for one run, staff_soft orders are removed from the end
of the seed list until one run fits under $3.50. The gate refuses any request that would pass the cap.
